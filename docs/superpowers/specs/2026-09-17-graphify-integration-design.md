# Graphify Integration Design

Date: 2026-09-17
Status: Approved design
Target repository: `Lamy210/Hono-Drizzle-Just`

## Objective

Add Graphify as an optional developer knowledge-graph tool without making it an application dependency, without adding Python or Graphify execution to the normal CI path, and without forcing assistant-specific hooks on contributors.

The integration must remain reproducible, reviewable, and safe for a public template repository.

## Scope

This change introduces:

- a pinned Graphify tool version;
- project-scoped cross-framework Agent Skill files generated by Graphify;
- repository-local Graphify ignore rules;
- `just` wrappers for common Graphify operations;
- developer documentation for installation, upgrades, assistant-specific opt-ins, hooks, and MCP;
- static tooling tests that enforce the repository integration contract.

This change does not add Graphify to `package.json` or `bun.lock`, does not commit generated knowledge-graph output, does not run Graphify in normal CI, and does not enable always-on, strict, MCP, or Git-hook behavior by default.

## Upstream and versioning

The upstream project is `Graphify-Labs/graphify`. The Python package is currently published as `graphifyy` while the CLI command remains `graphify`.

Initial pinned version:

```text
0.9.63
```

The repository stores the pin in `.graphify-version`.

Recommended local installation:

```bash
uv tool install "graphifyy==$(cat .graphify-version)"
```

A Graphify upgrade is an explicit reviewed change:

1. update `.graphify-version`;
2. reinstall that exact `graphifyy` version;
3. regenerate project-scoped Agent Skill files using the official CLI;
4. review the generated diff;
5. run the repository CI gates.

No custom fork of Graphify-generated skill content is maintained.

## Repository boundaries

Graphify is a development tool, not a runtime or build dependency.

The integration must not change:

- application runtime dependencies;
- Bun package dependency graph;
- PostgreSQL schema;
- production container composition;
- normal CI runner toolchain.

The Graphify feature is developed on a dedicated branch and pull request, separate from the in-progress idempotency feature.

Target branch:

```text
chore/graphify-integration
```

## Generated output policy

`graphify-out/` is local generated state and is never committed.

Add to `.gitignore`:

```gitignore
graphify-out/
```

The repository does not commit `graph.json`, `GRAPH_REPORT.md`, HTML output, cache files, wiki output, SVG, GraphML, or Neo4j exports from normal developer runs.

This avoids stale graph snapshots, large review diffs, merge conflicts, and accidental coupling between source changes and generated knowledge-graph state.

## Graphify source selection

Graphify already honors `.gitignore`. A repository-local `.graphifyignore` adds Graphify-specific exclusions.

The graph should include:

- `src/`;
- `tests/`;
- `drizzle/` SQL and metadata;
- `README.md`;
- architecture and development documentation;
- design specs under `docs/superpowers/specs/`.

The graph should exclude:

```gitignore
graphify-out/
docs/superpowers/plans/
```

Implementation plans are excluded because they are execution-oriented and frequently describe temporary state. Approved design specs remain included because they represent durable architectural intent.

Existing `.gitignore` exclusions such as `node_modules/`, `coverage/`, `.tools/`, and `dist/` remain the source of truth and are not duplicated unless Graphify behavior requires it.

## Assistant integration strategy

The repository default is portable Agent Skills rather than assistant-specific enforcement.

Generate and commit the official project-scoped Agent Skill using:

```bash
graphify install --project --platform agents
```

Expected repository content includes the official Graphify-generated Agent Skill under `.agents/skills/graphify/`, including `SKILL.md` and its generated references as produced by the pinned release.

The repository does not enable assistant-specific always-on hooks by default.

Claude Code, Codex, OpenCode, Cursor, Kiro, and other supported tools may be configured by individual developers using upstream-supported commands. These integrations are documented as opt-in because they can modify assistant behavior, project instruction files, or user-level configuration.

Codex users must be told that parallel Graphify extraction may require `multi_agent = true` under `[features]` in their user Codex configuration, according to upstream documentation.

## Hook policy

The following are opt-in and not installed by the repository integration:

- Graphify always-on hooks;
- strict source-read blocking hooks;
- `graphify hook install` post-commit hook;
- project/user assistant hooks that alter source-read behavior.

Reasons:

- hooks can affect every editor or agent interaction;
- `.git/hooks` is clone-local and not reliably distributed by Git;
- strict hooks can block or redirect normal source reads;
- a public template should not impose agent behavior on contributors.

Documentation may show upstream commands, clearly labeled optional.

## MCP policy

MCP integration is deferred from the initial Graphify pull request.

Graphify can expose an MCP server, but committing MCP configuration now would add assistant-specific configuration and another lifecycle dependency before the base CLI/skill integration has proven useful.

A later change may add MCP after the base integration is stable. It must be separately reviewed.

## Developer commands

Add thin `just` wrappers only. They must call the installed `graphify` executable and must not install or upgrade Python tools implicitly.

```just
graphify-build:
  graphify .

graphify-update:
  graphify . --update

graphify-query query:
  graphify query "{{query}}"

graphify-watch:
  graphify . --watch
```

The wrappers deliberately leave installation as an explicit developer action.

## Documentation

Create `docs/development/graphify.md` covering:

- purpose and when Graphify is useful;
- prerequisites and `uv`-based installation;
- exact version pin behavior;
- initial graph build and incremental update;
- querying and watch mode;
- where generated output lives and why it is ignored;
- `.graphifyignore` behavior;
- project Agent Skill regeneration;
- assistant-specific opt-in integrations;
- Codex multi-agent note;
- why strict hooks and post-commit hooks are not defaults;
- MCP as a future/optional integration;
- explicit upgrade procedure.

README may link to this guide, but the detailed operational instructions belong in the development guide.

## CI strategy

Normal CI must not install or execute Graphify.

Reasons:

- Graphify is a Python tool in an otherwise Bun-centered repository;
- some Graphify flows can use LLM/agent capabilities;
- graph generation is not a runtime correctness requirement;
- adding Graphify execution would increase runner cost and nondeterminism.

Instead, add a static tooling unit test, `tests/unit/tooling/graphify-integration.test.ts`, that verifies the repository contract.

The test must verify at minimum:

- `.graphify-version` exists and contains the expected pinned version format;
- `.gitignore` excludes `graphify-out/`;
- `.graphifyignore` exists and excludes `graphify-out/` and `docs/superpowers/plans/`;
- project-scoped `.agents/skills/graphify/SKILL.md` exists;
- Graphify command wrappers are present in `justfile`;
- the development guide names `graphifyy` and the project Agent Skill generation command;
- `package.json` does not declare Graphify/graphifyy as a dependency or devDependency;
- the integration does not require changes to `bun.lock`.

The test is intentionally static: it validates the repository integration contract without depending on a locally installed Python tool.

## Security and public-template considerations

Graphify-generated output may contain source-derived relationships or documentation-derived concepts, so output remains developer-local by default.

The integration must not:

- read or document real `.env` secrets;
- commit Graphify caches or generated graphs;
- introduce credentials or API keys;
- enable LLM-dependent automation in CI;
- cause assistant hooks to run without explicit developer opt-in.

The documentation should remind developers to review the input corpus before adding private or sensitive material outside the tracked repository.

## Acceptance criteria

The change is complete when all of the following are true:

1. `.graphify-version` pins Graphify `0.9.63`.
2. `graphify-out/` is ignored by Git.
3. `.graphifyignore` excludes generated Graphify output and implementation plans while retaining source/tests/design specs.
4. `.agents/skills/graphify/` contains files generated by the pinned official Graphify CLI.
5. `just graphify-build`, `graphify-update`, `graphify-query`, and `graphify-watch` are available.
6. `docs/development/graphify.md` documents installation, use, upgrades, assistant opt-ins, hooks, and MCP policy.
7. Static tooling tests enforce the Graphify integration contract.
8. `package.json` and Bun runtime/development dependencies do not gain Graphify.
9. Normal CI does not install or run Graphify.
10. Existing quality, coverage, contract, integration, E2E, and required jobs remain green.
11. The PR is reviewed before squash merge.
12. The exact merge commit on `main` passes the required CI jobs.

## Non-goals

The initial integration does not attempt to:

- commit a canonical repository graph;
- host Graphify output;
- add Neo4j;
- expose an MCP service by default;
- configure every supported assistant;
- enforce Graphify use before source reads;
- automatically run Graphify after every Git commit;
- add Graphify or Python dependencies to the application package manager.

## Future work

Potential follow-up changes, each requiring separate review:

- MCP configuration for selected assistants;
- optional always-on assistant integration;
- developer-local post-commit graph refresh;
- graph quality evaluation for this repository;
- a lightweight version-update automation if Graphify stabilizes its release cadence.
